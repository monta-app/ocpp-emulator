# PR description

**Title:** Fix RemoteStopTransaction being permanently rejected when the CSMS reuses a transaction id

# Intent

## What should this change accomplish?

`RemoteStopTransaction` must succeed for the transaction that is actually in progress, even
when an older, already-completed transaction previously used the same CSMS-assigned
`externalId`.

- Done when `ChargePointTransactionRepository.getByExternalId` only ever matches a
  still-open transaction (`endTime == null`) for a given `externalId`.
- Done when a regression test reproduces the original failure — a completed transaction and
  a brand-new, still-open transaction sharing the same `externalId` — and demonstrably fails
  against the pre-fix code and passes against the fix.

## Scope / non-goals

- Touches only `ChargePointTransactionRepository.getByExternalId`
  (`chargepoint/transaction/repository/`) and adds a `jvmTest` regression test for it.
- `SmartChargingClientHandler.setChargingProfile` (`SetChargingProfile` for a `TxProfile`)
  calls the same repository method for the same reason (a charging profile targets a live
  transaction), so it benefits from the fix automatically — no separate change needed there.
- Does **not** add a database-level uniqueness constraint on `externalId`, and does **not**
  scope the lookup by charge point / connector — the existing `isOwner()` checks at both call
  sites already guard against a match belonging to the wrong charge point. Left as a possible
  follow-up rather than bundled into this fix.

## Why?

### The bug

A developer testing against their CSMS backend ("OmniEV") reported that `RemoteStopTransaction`
was being rejected by the emulator every single time, for every transaction, even though
their CSMS never sees this with real charge points — only with this emulator. The emulator
logs showed:

```
[...] - [ERROR] - [...ChargePointLogger] -  - [2] charge already ended, rejecting
```

on the **very first** `RemoteStopTransaction` received for a transaction that had only just
started charging — before any real stop had ever happened. The CSMS retried every ~5 seconds
and was rejected every time:

```
13:59:04,910 receive [3,"...",{"status":"Rejected"}]  <- RemoteStopTransaction #1, immediately rejected
13:59:10,040 receive [3,"...",{"status":"Rejected"}]  <- RemoteStopTransaction #2
13:59:15,187 receive [3,"...",{"status":"Rejected"}]  <- RemoteStopTransaction #3
13:59:20,437 receive [3,"...",{"status":"Rejected"}]  <- RemoteStopTransaction #4
13:59:25,600 receive [3,"...",{"status":"Rejected"}]  <- RemoteStopTransaction #5
13:59:30,741 receive [3,"...",{"status":"Rejected"}]  <- RemoteStopTransaction #6
```

The charge only actually stopped a few seconds later, via a **local** stop
(`"reason":"Local"` in the `StopTransaction` sent to the CSMS) issued through a different
code path than `RemoteStopTransaction` — i.e. the connector's real, live transaction was
never the one being looked up by the rejected `RemoteStopTransaction` calls.

### Root cause

`RemoteStopTransaction` resolves the target transaction via
`ChargePointTransactionRepository.getByExternalId(externalId)`:

```kotlin
fun getByExternalId(externalId: Int): ChargePointTransactionDAO? {
    return ChargePointTransactionDAO.find {
        ChargePointTransaction.externalId eq externalId
    }.firstOrNull()
}
```

`externalId` is not generated by the emulator — it is whatever integer the CSMS returns in
the `StartTransaction` confirmation
(`ChargePointConnectorExtensions.onStartSuccess`: `externalId = confirmation.transactionId`).
OCPP 1.6 only supports numeric transaction ids, and it is common for CSMS test/dev backends
to reset their id counter between sessions (fresh test database, service restart), so small
ids get reused across otherwise-unrelated test runs.

The emulator's own SQLite database, on the other hand, is deliberately persistent — it lives
under `~/monta/` and survives restarts, so it accumulates the full transaction history of
every session ever run against it, with no uniqueness constraint on `externalId`.

Put those two together: once the CSMS reuses an id that already exists in the emulator's
local history (from an earlier, completed transaction), `getByExternalId` can match either
row — and with no `ORDER BY`, it returns rows in essentially insertion order, i.e. the old,
already-ended one. `ChargePointTransaction.canStop()` (`endTime == null`) then evaluates
against that stale row, sees `endTime` already set, and rejects — every time, forever, since
that row's `endTime` can never become null again. Meanwhile the connector is charging on a
different, correct, still-open row that this lookup never finds.

### Why this matters beyond one developer's session

This isn't specific to one CSMS implementation. Any team using this emulator to test their
CSMS's remote-start/remote-stop flows against a backend whose transaction-id sequence isn't
strictly monotonic forever (test fixtures, database resets between CI runs, service
restarts) will eventually hit this, silently, and lose the ability to test
`RemoteStopTransaction` at all until they notice and wipe or swap the emulator's local
database — the current *workaround*, not a fix. The bug is intermittent and looks like a
timing/race issue from the outside (it stops reproducing once the CSMS's id counter moves
past the range of ids already on file), which makes it particularly easy to lose time to.

## How was it built and verified?

- Diagnosed by comparing emulator-side and CSMS-side logs for a working charge session
  against a failing one, isolating the divergence to the very first `RemoteStopTransaction`
  being rejected before any real stop had occurred — evidence that a stale DB row was being
  matched instead of the live transaction.
- Fix: filter `getByExternalId` to `endTime == null`, matching the idiom already used
  elsewhere in this codebase for "the currently open transaction"
  (`ChargePointDAO.getActiveTransactions()`, `ChargePointConnectorDAO.activeTransactions`).
- Added `ChargePointTransactionRepositoryTest` (2 cases) against a real Exposed/SQLite
  in-memory database: one seeds a completed transaction and a live transaction sharing the
  same `externalId` and asserts the live one is returned with `endTime == null`; the other
  asserts a completed-only `externalId` now correctly returns `null` rather than the ended
  row. Verified both tests fail against the pre-fix code (`AssertionFailedError`, reverted
  the fix locally and reran) and pass against the fix.
- Ran `./gradlew ktlintCheck` (clean) and `./gradlew :app:jvmTest` (full suite green).
- Not verified against a live CSMS backend from this environment — verification is via the
  regression test, which replays the exact database state (a completed transaction and a new
  transaction sharing an `externalId`) that produced the failure logs above.
